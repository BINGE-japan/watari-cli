# ワタリの記憶設計 — 先行研究の"いいとこ取り"ロードマップ（post-MVP）

> **設計記録**（参照用ロードマップ。現在の仕様は [SPEC.md](../../SPEC.md)）。
> 利用者向けの文書ではありません。

Status: reference / post-MVP roadmap（実装対象ではない）

ワタリの記憶は「**log（追記専用の正本）→ State（log から決定論で再生成する今の顔）**」の2段構成です。
強みは決定論・監査可能・可搬・ゼロ依存にあります。先行研究からは**概念だけ借り、機構（特に
embedding / vector 検索）は採りません**。本ドキュメントは、その方針で将来取り込む候補を整理した
参照用ロードマップです。

## 借りる概念

- **reflection**（Generative Agents, Park et al., 2023）：定期的に記憶を横断して高次の洞察を合成する仕組み。
  ワタリ流は、夢のときにモデルが「X に繰り返し戻っている」「この3 thread は実は一案件」等を合成し、
  それを**普通の記憶行として保存**します（新しい機構は不要）。
- **retrieval スコア**（Generative Agents）：`recency × importance × relevance`。State を「載る/載らない」の
  二値でなく、**強さで並べる連続ランク**に寄せます。importance は記録時の stakes、recency は last、
  relevance は下記で実現します。
- **hot/cold メモリのページング**（MemGPT, Packer et al., 2023）：hot な作業集合と cold な archive に分け、
  必要時に cold を呼び戻します。State から「沈めた」ものを、関連が来たら前面に戻す形です。
  log 全読み regen のスケール対策にもなります。

## 採らない機構と理由

- **embedding / ベクトル検索（vector-RAG）は採りません**。理由は次の4点です。
  1. 決定論が死ぬ（埋め込みモデルのドリフトで想起が変わり、再現できない）
  2. 監査不能（なぜ想起したかを説明できない）
  3. 可搬性が濁る（記憶がベクトル・再埋め込みに依存する）
  4. ゼロ依存が壊れる
- relevance は、**構造化クエリ（topic / domain / tags / kind の一致）＋走っているモデル自身の推論**で
  実現します（別途の検索エンジンは作りません）。
- 認知の「**7±2 の容量上限**」も採りません。必要なのは容量制限ではなく関連性だからです。

## MVP との線引き

- 議題2の**忘れ方 MVP**（実時間の時計・旧クローズ閾値で"消さず声かけ（最近どうなってる？）"・
  低 stakes は黙って沈める・寿命は項目ごと）は**別途決定済み・実装対象**です。
- 本ドキュメントの3概念（reflection 合成・連続スコア・hot/cold ページング＋構造化 relevance）は
  **すべて post-MVP** です。
- 墓場化（cold な log が溜まるだけで活かされない問題）を最終的に解くのは、
  **「構造化 relevance で archive を呼び戻す」**ことです。
