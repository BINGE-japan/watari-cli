# ADR-011: physical object layout benchmark contract

Status: proposed; no physical layout selected
Issue: D011
Depends: D003, B000
Decision owner: G003 high-trust reviewer after G001/G003 observations
Executable contract: `tests/performance/storage_harness.py`

## Decision

D011 does not choose a physical layout. It freezes a reproducible comparison
between two candidates:

1. `loose-encrypted-object-candidate.v1`: one immutable qualified-codec output
   per file;
2. `immutable-pack-segment-candidate.v1`: 256 identical qualified-codec outputs
   per content-addressed immutable segment.

Those descriptions name the eventual physical targets. The D011 executable
stores only deterministic synthetic stand-ins and cannot ingest qualified-codec
output.

The decision remains `proposed` until D010 qualifies a codec, G001 adds and
reviews a separate versioned corpus-input contract, G001 observes both layouts
with one identical audited corpus on Ubuntu 24.04 / WSL2 at 10,000 and 100,000
events, and G003 repeats the selected codec/layout artifact. A D011 dry run,
self-test, or synthetic scale run is non-authoritative and cannot close
`DEC-OPEN-005`.

The later selection rule is frozen but is not applied here:

- if the loose candidate passes every common and layout-specific budget, G003
  may select loose;
- otherwise, if the pack candidate passes every budget, G003 may select pack;
- if neither passes, no layout is selected and the design must be revised;
- a result does not authorize selection unless its exact codec artifact,
  filesystem observation, plan digest, and G001/G003 evidence are reviewed.

This preserves D003 logical event bytes and identifiers. Physical layout,
encryption envelope, compression, and remote locator construction remain
outside D003. Logical event IDs and payload digests must never become plaintext
remote filenames.

## Safety and authority boundary

The executable harness:

- uses generated byte strings with no semantic content;
- creates every file below a fresh `tempfile.TemporaryDirectory`;
- removes each worker root on success and failure;
- emits JSON only to standard output and writes no report file;
- performs no network access, credential access, live Watari/state read, home
  discovery, mount-source collection, or external write;
- does not implement or claim encryption. Its SHA-256 counter stream is only an
  opaque, deterministic stand-in used to test the physical algorithms.

The current executable is synthetic-stand-in-only. It has no authoritative
input mode, codec adapter, corpus path, or external-codec execution boundary.
Its `--run` output remains non-authoritative even if all budgets pass. G001 is
forbidden from treating this harness or its result schemas as codec evidence.

After D010, G001 must introduce and review a different versioned corpus-input
contract and its implementation before any authoritative layout run. The
reserved future schema name is `watari.storage-corpus-input.future.v1`; it is a
name and required-field reservation, not an implemented schema. Its closed
object must contain exactly these required fields before promotion to a real
version:

```text
schema_version
status
codec_artifact_digest
corpus_artifact_digest
event_count
payload_bytes
payload_stream_sha256
ordered_payload_lengths_sha256
prestage_duration_ns
```

That future contract must materialize and verify the corpus once, bind the
codec and corpus artifact digests, and feed the same read-only ordered bytes and
lengths to both layout processes. Codec setup/encryption pre-stage time is
excluded from layout durations and reported separately as
`prestage_duration_ns`. A future revision may change that timing boundary only
by changing the contract version. D011 adds no arbitrary local-file read
facility.

The harness deliberately does not accept an arbitrary input directory, output
directory, command, plugin, credential reference, or network endpoint. This
prevents a dry design ticket from becoming a live-state benchmark interface.

## Frozen plan schema

`watari.storage-benchmark-plan.v1` is a closed JSON object with exactly these
top-level members:

| member | v1 rule |
| --- | --- |
| `schema_version` | exact `watari.storage-benchmark-plan.v1` |
| `status` | exact `non-authoritative` |
| `decision` | exact `proposed` |
| `authority_gate` | exact `G001-and-G003-observation-required` |
| `platform_scope` | Linux, Ubuntu 24.04, WSL2, Python 3.11+ |
| `fixed_seed` | exact integer embedded by the harness |
| `event_counts` | exact ordered list `[10000, 100000]` |
| `codec_input_policy` | D011 synthetic-only mode, authoritative-run prohibition, reserved future corpus fields, exact equality rule, and no arbitrary local corpus read |
| `layouts` | the two exact candidates above, in fixed order |
| `payload_distribution` | exact deterministic distribution and 1/32/10k/100k byte-total/stream-digest goldens below |
| `measurement` | exact operation/order/repetition contract below |
| `metrics` | exact duration/scalar metric allowlists below |
| `filesystem_metadata` | exact metadata allowlist below |
| `budgets` | versioned common and layout-specific limits below |
| `cleanup` | temp-only, no-network/no-credential/no-live-state policy |

Every nested object is closed as well. Unknown or missing members, schema
versions, layouts, metrics, operations, scales, statistics, or safety policies
fail validation. Numeric booleans and truthy strings are not accepted as JSON
booleans. All integer fields, including the fixed seed and nanosecond values,
must remain in D003's interoperable JSON safe-integer range.

`--validate` includes explicit rejection vectors for unknown schema, layout,
plan/sample metric/member, cache policy, changed budget, duplicate JSON member,
false platform claim, cross-device root, sample seed/repetition drift,
cross-layout input/environment mismatch, merge/corruption invariant drift,
forged budget, and malformed suite. Result samples, input/environment
aggregates, summaries, budget checks, and suites have exact member sets. The
validator recomputes aggregates, summaries, and budgets from samples and frozen
limits; a caller cannot substitute unmeasured values.

The plan digest is `sha256:` followed by SHA-256 of the plan serialized as
ASCII JSON with recursively sorted keys, no insignificant whitespace, and the
exact embedded scalar values. It identifies this benchmark plan only. It is not
a D003 event, payload, context, policy digest, signature, or trust decision.

## Identical synthetic input

The fixed payload distribution is:

| exact bytes per codec-output stand-in | weight |
| ---: | ---: |
| 256 | 50 |
| 1,024 | 30 |
| 4,096 | 15 |
| 16,384 | 5 |

The weights total 100. Bucket selection and bytes are derived from the fixed
seed, branch label, and event ordinal with a SHA-256 counter stream. There is no
compression and no semantic plaintext. The generator is deterministic and
streamed per event, so 100,000 payloads need not be retained in memory.

The fixed main-branch goldens are:

| events | payload bytes | framed-stream SHA-256 |
| ---: | ---: | --- |
| 1 | 256 | `a647691d3ea3fdb332acabd03308da3fafa7d539a3bda7e17cdb7a92c4459dde` |
| 32 | 64,256 | `bc623f60e320f3db34be71e48cc75563c07b2663971e07a8a7613a3902fdb092` |
| 10,000 | 18,362,368 | `ae8b579c8ecbafd4be2d3932a1c35b6ef9f327fbdb687a1e9b7b3bea6b4c3fdd` |
| 100,000 | 187,856,128 | `4d37f3a6428cff471f7f23efc23144ce5d3d972517f22d0a0f64b44762472eda` |

For every measured repetition:

- both layouts receive the same main-branch event order, byte lengths, and byte
  strings;
- `payload_bytes` must equal the total recomputed from the fixed generator;
- `payload_stream_sha256` hashes each unsigned 64-bit big-endian length followed
  by its payload, thereby binding bytes, lengths, and order; samples must match
  the frozen 1/32/10k/100k golden for their fixed scale;
- every measured sample must have one identical byte total and stream digest;
- a loose file and a pack record contain the same payload bytes;
- the pack adds only its magic and per-record locator/length framing;
- the loose locator is derived from the opaque stand-in bytes, never from a
  logical Watari ID;
- the current executable has no mechanism for substituting real codec output.

The plan stores the exact byte total and framed-stream SHA-256 for 1, 32,
10,000, and 100,000 events. The 1/32 generator paths are regenerated by
`--validate`; the 32-event executable self-test also proves the write path
against its golden. A later 10k/100k synthetic run must match the frozen scale
goldens before its samples are accepted. Changing a golden requires a new plan
revision and digest.

## Candidate representations

### Loose candidate

The candidate writes one immutable regular file per payload below `objects/`.
Every file is flushed with `fsync`, then the object directory is flushed. A
small revision head is canonical benchmark metadata. `index.json` is derived,
excluded from repository-size and backup measurements, and must be rebuildable
from object filenames.

Its corruption failure-domain proxy is one event and the exact bytes of that
one codec output.

### Immutable pack candidate

The candidate appends at most 256 records to a temporary segment, flushes it,
renames it to the SHA-256 of the complete segment bytes, and flushes the segment
directory. Committed segments are never rewritten. Each record contains a
32-byte opaque locator, an unsigned 64-bit big-endian payload length, and the
same payload bytes used by the loose candidate.

`index.json` maps opaque locators to segment, offset, and length. It is derived,
excluded from repository-size and backup measurements, and rebuilt by parsing
segment framing. The corruption failure-domain proxy assumes one authentication
unit per segment, so one failed segment affects at most 256 events and their
combined payload bytes. G001 must replace this proxy with the observed failure
domain of the exact qualified codec/container construction under the future
corpus contract, not by extending the D011 run in place.

The two candidate algorithms avoid representation-independent asymmetric
overhead: duplicate-locator checks use a set in both create paths, and status
performs one filesystem metadata lookup per physical storage unit. Pack index
records sharing a segment reuse that lookup; record bounds are still checked
individually.

## Measurement protocol

### Scale, order, cache, and isolation

- qualification scales are exactly 10,000 and 100,000 events;
- one warmup cycle is discarded and six measured cycles are retained, giving
  each layout three first-position and three second-position measurements;
- each layout/repetition runs in a fresh Python process and fresh temporary root;
- the parent owns an outer temporary supervisor root, attests it with a fixed
  marker, and removes it after the child exits or times out; the child may only
  create its nested worker root there;
- each worker has a fixed 7,200-second safety timeout, large enough for the sum
  of the frozen 100k operation ceilings and untimed setup;
- the first layout alternates each cycle to reduce fixed order bias;
- timing uses `time.perf_counter_ns`;
- the harness never invokes privileged cache dropping. Results describe one
  warmup followed by the filesystem cache as observed;
- median is nearest-rank p50 and p95 is nearest-rank p95. Both are integers;
- qualification results require the fixed seed, scales, repetitions, layout
  order, and 256-event comparison segment limit. Tuning them creates a different
  schema revision, not a comparable result.

### Timed operations

Every duration is reported in nanoseconds.

| metric | exact measured boundary |
| --- | --- |
| `create` | generate the fixed payload stream, write canonical units, file/directory `fsync`, write head and rebuildable index |
| `status` | validate the exact head/index schemas, event count, bounded relative paths, referenced regular files, offsets, and lengths |
| `clone-equivalent` | copy and `fsync` canonical head/objects into an empty local root, rebuild the excluded index, then run status |
| `copy` | local `shutil.copytree` of the complete working tree, including the derived index, followed by destination file/directory `fsync` |
| `pull-equivalent` | start from an aligned 90% prefix, copy and `fsync` only missing immutable units and the head, rebuild the index, then run status |
| `rebuild` | delete the derived index, reconstruct it only from canonical units, then run status |
| `backup` | create, file/directory `fsync`, and reopen an uncompressed tar containing canonical head/objects only; links are rejected |

`clone-equivalent` and `pull-equivalent` are local filesystem proxies. They do
not claim Git or network performance. Pull uses the same aligned base event
count for both candidates; it never edits an already committed object or
segment.

Preparation of the pull base is outside the timed pull boundary. Cleanup and
temporary diagnostic probes are outside all operation durations. Every worker
must report successful root removal before its sample is accepted.

## Metrics schema

`watari.storage-benchmark-sample.v1` has an exact schema. It binds layout,
event count, seed, repetition, warmup flag, shared comparison segment limit,
pull base, durations, fixed-generator byte total, framed payload-stream digest,
footprint, merge/corruption proxies, peak RSS, filesystem metadata, and cleanup.

Required duration metrics are exactly:

```text
create
status
clone-equivalent
copy
pull-equivalent
rebuild
backup
```

Required scalar metrics are exactly:

```text
payload_bytes
repo_size_bytes
working_size_bytes
inode_count
file_count
mergeability_proxy_conflicting_paths
single_corruption_blast_radius_events
single_corruption_blast_radius_bytes
peak_rss_bytes
```

Definitions:

- `payload_bytes` is the sum of identical synthetic codec-output bytes, without
  layout framing, and must equal the fixed generator's recomputed total;
- `repo_size_bytes` is logical `st_size` for the revision head and immutable
  objects/segments; the derived index is excluded;
- `working_size_bytes` is allocated regular-file space from `st_blocks * 512`,
  including the derived index;
- `file_count` counts all regular files in the candidate working tree;
- `inode_count` counts unique `(st_dev, st_ino)` pairs for regular files and
  directories in the candidate working tree;
- `peak_rss_bytes` converts Linux `ru_maxrss` KiB to bytes and is isolated by
  the per-layout worker process.

Every scalar and every duration has `median` and `p95`. The stream digest is
input evidence rather than a scalar statistic. Samples remain in the result for
audit. The validator recomputes every summary and requires all samples across
both layouts to have the same byte total and stream digest.

### Mergeability proxy

The harness creates two two-event append-only synthetic branches from distinct
branch labels and compares canonical relative file paths and file SHA-256
values; the derived `index.json` is excluded. It reports branch event count,
identical paths, conflicting paths, left/right-only paths, and union paths. The
budgeted scalar is conflicting paths.

The validator fixes `branch_append_events` at two and checks the exact path
counts implied by the layout and segment limit, including
`union = conflicts + identical + left-only + right-only`.

This measures physical path collision pressure only. It is not a semantic Git
merge, signature, CAS, or conflict-resolution test. G001/G003 must retain Git
and transaction tests separately.

### Single-corruption blast radius

After all timed operations, the harness flips one bit in the storage unit that
contains generated event zero and verifies that the unit digest changes. It
reports the exact event count and fixed-generator payload byte total in that
candidate authentication-unit proxy. The validator recomputes both. The probe
does not claim AEAD tamper handling or recovery; D010/G001 must repeat wrong-key
and tamper tests under the future authoritative contract.

## Filesystem and runtime metadata

Each sample records exactly:

```text
system
release
machine
distribution_id
distribution_version_id
python_implementation
python_version
wsl2_detected
required_platform_match
statvfs_block_size
statvfs_fragment_size
statvfs_name_max
filesystem_type
cache_policy
temp_root_device_id
temp_root_same_device
```

Filesystem path inspection is limited to the synthetic temporary root through
`statvfs`/`stat`. The only allowlisted host metadata read is Python's standard
`freedesktop_os_release()` for non-secret distribution ID/version. Python's
standard library does not expose a portable filesystem-type name, so D011 emits
the explicit value `unavailable-in-python-standard-library` and does not read or
report mount sources. `cache_policy` must be exactly the frozen as-observed
policy. `temp_root_device_id` is `st_dev` for the synthetic worker root and is
used only to prove that compared workers used the same device. A result is
rejected unless every environment field is identical across all compared
samples. `required_platform_match` requires Linux, the WSL2 kernel marker,
Ubuntu 24.04, and Python 3.11 or newer. G001's private observation record must
independently record the exact Ubuntu release, WSL version, filesystem
type/options, CPU, memory, storage medium, power mode, codec artifact digest,
and whether another process affected the run. Those observations must not be
guessed or inserted into the product repository; G001 keeps them in its
approved private audit store.

The scale harness rejects observations outside that complete platform scope
even if the synthetic program itself completes. A self-test may run on another
platform but remains non-authoritative.

## Result and suite closure

`watari.storage-benchmark-result.v1` is closed and always has status
`non-authoritative` and decision `proposed`. It contains the fixed run config,
samples in exact layout/repetition order, recomputed input and environment
consistency objects, summaries, budget evaluation, and cleanup evidence.

`watari.storage-benchmark-suite.v1` is also closed. Its exact members are
`schema_version`, `status`, `decision`, `plan_digest`,
`environment_consistency`, and `reports`. Reports must be exactly one validated
synthetic-scale result for 10,000 followed by one for 100,000 events, with no
missing, duplicate, or reordered scale and the same plan digest as the suite.
The suite recomputes one environment aggregate across every sample in both
scales and requires exact runtime, filesystem, and device metadata equality.
Unknown suite members, a forged digest, report reordering/duplication, and
cross-scale environment drift have explicit rejection vectors. The suite
remains synthetic and non-authoritative.

## Frozen budgets

All thresholds apply to p95. Passing a budget only makes a candidate eligible
for G003 review; it never changes `decision` from `proposed`.

### Common duration and resource limits

| events | create | status | clone-equivalent | copy | pull-equivalent | rebuild | backup | repo size | working size | peak RSS |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 10,000 | 120 s | 15 s | 90 s | 60 s | 45 s | 45 s | 90 s | 512 MiB | 1 GiB | 512 MiB |
| 100,000 | 1,200 s | 120 s | 600 s | 600 s | 300 s | 300 s | 900 s | 4 GiB | 6 GiB | 2 GiB |

At both scales, logical repository size must also be at most 2:1 versus payload
bytes and allocated working size at most 4:1. Integer cross multiplication is
used; no floating-point ratio enters the result schema.

### Layout-specific limits

| layout | files at 10k / 100k | inodes at 10k / 100k | merge conflicting paths | corruption events | corruption bytes |
| --- | ---: | ---: | ---: | ---: | ---: |
| loose | 10,010 / 100,010 | 10,020 / 100,020 | 1 | 1 | 16,384 |
| pack | 50 / 410 | 60 / 420 | 1 | 256 | 4,194,304 |

All common and layout-specific checks must pass. Unknown, missing, duplicate,
or reordered budget metrics fail closed, as does a `passed` flag inconsistent
with its observed value and limit.

These budgets are generous qualification ceilings, not product release SLOs.
Q003 later fixes release-regression thresholds from observed qualified results.

## Executable modes

All commands use only the Python standard library:

```text
python3 tests/performance/storage_harness.py --validate
python3 tests/performance/storage_harness.py --dry-run
python3 tests/performance/storage_harness.py --self-test
```

- `--validate` performs no benchmark write. It validates the embedded plan and
  runs closed-schema positive/negative vectors.
- `--dry-run` performs no benchmark write. It validates and prints the exact
  10k/100k plan.
- `--self-test` runs 32 synthetic events, one warmup, and three measured cycles
  with eight-event pack segments. It validates algorithms, schemas, subprocess
  isolation, metrics, and cleanup; its result validator requires exactly
  32/1/3/8 and scale budgets are explicitly not applicable.
- `--run` runs the non-authoritative synthetic 10k and 100k scale plan and
  validates its closed suite before printing. D011 does not run it. It has no
  external corpus mode, and G001/G003 must not treat it as crypto qualification
  evidence.

The hidden worker accepts only the two allowlisted layout IDs and explicit
integer parameters supplied by the parent. It has no path, command, or provider
input and refuses to run outside the parent-attested synthetic supervisor root.
The root must be an owner-only, non-symlink child of Python's temporary root.
Errors return a nonzero exit and no fallback layout is selected.

## Acceptance and future closure

D011 is complete when:

1. `--validate`, `--dry-run`, and the small `--self-test` pass with both
   `python` and `python3`;
2. unknown schema/layout/metric/member vectors are rejected;
3. D003 canonical vectors still pass unchanged;
4. only this ADR and the harness changed;
5. no 10k/100k result is represented as observed evidence.

After D010, G001 must first implement and review the separate versioned corpus
contract reserved above. Only that later contract may record authoritative 10k
and 100k results for every audited codec × layout pair, including the corpus
and codec artifact digests, separately reported pre-stage time, all samples,
plan digest, budgets, cleanup, platform, and private environment evidence. G003
repeats the exact candidate artifacts, reviews corruption/wrong-key behavior,
and only then changes this ADR from `proposed` to a selected physical layout.
