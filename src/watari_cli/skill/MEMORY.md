# 記憶の保存・整理（作業時だけ読む）

通常の会話・検索だけのときはこの文書を読み込む必要はありません。人格と安全境界はSKILL.mdに従います。
この文書は保存判断と整理手順の一か所の説明です。行の詳しい仕様は同じフォルダのSCHEMA.mdです。

## 専用道具で現在の発話を覚える

1. 自動で渡された記憶で足りなければ `watari_memory_search` / `watari_memory_get` で既存の話題・key・domainを確認します。
2. `watari_memory_prepare(scope="current")` で現在の本人発話とbatch_idを取得します。直近の本人発話だけが対象です。過去の発話を今回の発話の根拠に付け替えず、過去分にはconversationsまたは従来の手順を使います。
3. 下の基準で残す内容を選び、 `watari_memory_save` にbatch_idとdecisions_jsonを渡します。日時・出所・参照先・作成元は道具が設定するので指定しません。保存・検査・既存のGit同期も固定処理が行います。
4. savedとcheckedがtrueであることを確認してから報告します。同期警告やincomplete_sourcesがある場合は完全終了と報告しません。

`decisions_json` はJSON配列の文字列です。各本人発話のuuidにつき一つの判断を渡します。残さない発話も `rows:[]` を明示します。assistantは文脈専用で、判断対象には入れません。

```json
[{"uuid":"取得結果のuuid","rows":[{"kind":"thread","topic":"既存名に寄せた話題","summary":"本人の決定と根拠の要点。","note":"現在の予定や状態。"}]}]
```

各rowsの内容はSCHEMA.mdの行仕様からts/source/refsを除いたものです。kindとsummaryは必須で、種類ごとの必須項目も満たします。
一つの発話から同じkindを二件には分けません（既存の重複防止単位がuuid×kindのため）。
新しい学習分野が本当に必要な回だけallow_new_domain=trueを指定します。

- 検証に失敗したら内容を直して材料を取得し直します。同じbatch_idで違う内容を送ってはいけません。
- 中断時は保存済みの可能性があります。同じID・同じ内容で再確認し、二重保存しません。
- batch_idは同じセッション・同じ記憶フォルダで30分だけ使えます。再起動や会話の分岐変更では失効します。失効時は材料を取り直し、既存記憶と照合します。
- 根拠の紐付けは要約内容の正しさを保証しません。原文にない判断や意図を足さないでください。
- 画像本文はこの道具では取得しません。omitted_imagesがある発話の画像内容を、確認済みとして記憶しません。

## 会話全体の記憶の整理

途中経過と確認質問は出しません。最終報告は1行です。

1. `watari_memory_prepare(scope="conversations")` で未処理の会話を取得します。最大40件を目安に同時刻の発話を分断せず、全体32KB以内で返します。大きすぎる同時刻の一群は切り捨てず失敗するため、下の従来手順で範囲を確認します。
2. 各本人発話について残す／見送るを判断し、上と同じ `watari_memory_save` で確定します。読み取り済み時刻の引数を組み立てる必要はありません。
3. truncatedの対象が残る場合は続きの材料を取得します。読取失敗は未処理のまま残します。同じ失敗を無限に繰り返しません。
4. **接続サービスは別です。** この会話用の道具だけで全サービスを整理したことにはしません。下の従来手順4で読み取り・選別・保存し、最後に検査します。接続したPCだけが担当する規則を維持します。
5. 保存・検査結果と未処理対象を確認し、「整理しました。新しくN件覚えました。」等と1行で報告します。何も覚えない回も正常終了できます。失敗が残った場合は工程を明示します。

専用道具は既存CLIの便利な入口であり、安全化版の権限分離の代替ではありません。MCP・新しいモデル呼び出し・新しい保存先は使いません。

### 何を残すか（三層）
- **必ず拾う**: 決定・約束・期限・本人やアカウントの事実・状態変化・**指示/好み/作業スタイル**
  （「X してほしい」「Y するな」「こう呼んで」等）。
- **必ず捨てる**: 純粋な作業依頼・デバッグ・相づち・**変わっていない既知**。
- **迷ったら軽く拾う**: 全文は要らない。「いつ・何を話したか＋元へのポインタ」の軽い記録で足りる。
  （整理中は確認しない。**会話の最中**に重要そうで初耳の事実が出たときだけ、
  「覚えておきますか？」と確認してから記録してよい。）

### 環境の記録
- 全パソコン共通（ユーザー自身の事実・使うツール）→ `fact` の `profile:{key,value,mode:"relevant"}` へ。
- `mode:"always"` は、呼び方・応答形式・確認境界など**どの話題でも毎回効く**好みだけ。職歴・会社・事業・ツール・個別運用は安定事実でも `relevant`。
- 特定のパソコンだけの環境 → host 記録（`watari host --set KEY=VALUE`）へ。
- localhost・127.0.0.1・端末固有パスは作成元のパソコンに属する。記憶項目の `origin` と現在の
  `runtime_context` が一致し、実際に到達可能と確認できた場合だけ利用可能な場所として案内する。
  `origin` が無い場合は記憶の記録にある `refs` を確認し、作成元不明の場所を現在使えるものとして案内しない。

### 六つの規律
1. **機密・秘密**: 記憶は git で同期され得る。**秘密そのもの（パスワード・API キー・口座番号・
   カード番号）は記録しない**。記録してよいのは「A 銀行に口座がある」レベルの事実まで。
   機微だが残すべき事実（収入・健康・住所）は note を「【機密】」で始め、こちらから軽々しく
   話題にしない。ユーザーが特に機微な話を始めたら、同期設定がある場合は
   「この内容も記憶に残ります。残さないほうがよければ言ってください」と一言伝えてよい。
2. **根拠**: 記録の根拠は本人の発話か、接続サービスの実際の状態だけ。推測・一般論は記録しない
   （どうしても要るなら "推測" と明示）。assistant の説明は、本人が採用・同意した確認にのみ使う
   （説明された ≠ 学習した）。
3. **寄せる・上書き**: 記録前に自動確認済みの記憶と `watari_memory_search` / `watari_memory_get` で既存を確認（専用道具が無ければ `watari recall`）→ 新規＝足す / 同じ＝捨てる /
   違う＝更新（新しい値を現在値に。古い値は記録の履歴に残る）。`interest`/`thread` の topic・
   `study` の domain・profile の key は**必ず既存名に寄せる**（名前違いの新設は二重管理）。profile の内容が同じでも mode を直す移行は新しい行として正当。
4. **丸写ししない**: メール・課題・文書の中身は接続先が原本。記憶には**要点＋ポインタ**だけ。
5. **好み・作業スタイルは事実と同格**: 指示・呼び方・進め方の希望は「必ず拾う」に含める。
6. **完了・締めも状態変化**: 果たされた約束・過ぎた期限・終わったタスクはクローズを記録する
   （`thread` は `status:"closed"`。リマインドから外れる合図になる）。

### 書き方
- `note` は state 用・**現在形 1〜2 文**（経緯・根拠・時系列は `summary` へ）。
  profile 行には mode を必ず付け、always は毎回答に必要なもの、relevant は話題に応じて検索するものとする。
  mastery: 1＝紹介に本人が反応 / 2＝自分の言葉・成果物で再構成 / 3＝別セッションで再現。
- 同一発話から life と learning の両方に書くのは正当（重複除去の単位は uuid×kind）。
  理解の中身は learning、関心の熱は life.interest（同文を両方に書かない）。
- 行仕様・本物の発話の選別・重複除去・note の記述規約の正本は同梱の `SCHEMA.md`。
  機械処理を手でなぞらない。


## 従来のCLI手順（専用道具がない場合・サービスの整理）

1. **抽出（機械）**: `watari scan --json` を実行する。出力は
   `stores.{pi, cloud_<machine>, …}.{readable,count,max_ts,truncated}` と `messages[]`（ts 昇順）。
   `stores.cloud_<machine>` は他のパソコンから同期された発話。`messages[]` には発話元の
   `machine` / `computer` / `runtime` と、`role:"assistant"` の行も含まれる。assistant行は判定の
   **文脈用**——記憶の根拠は本人（`role:"user"`）の発話だけ。
2. **判定（あなた）**: あとで役に立つものだけを SCHEMA の行仕様で JSON 配列にして
   一時ファイルへ書く（0 件なら `[]`）。発話由来の行は `machine` / `computer` / `runtime` を
   `refs` へコピーする。基準は下の「三層」「六つの規律」「書き方」。
3. **取り込み（機械）**: `watari ingest --rows <file>` に、次の規則でフラグを足して実行する:
   - `stores.pi` の `readable` が true かつ `max_ts` が null でない
     → `--advance-pi <stores.pi.max_ts>` を付ける。
   - `stores.cloud_<machine>` ごとに、`readable` が true かつ `max_ts` が null でない
     → `--advance-cloud <machine>=<max_ts>` を **1 ストアにつき 1 つ**付ける。
   - 条件を満たさないストアのフラグは**付けない**（据え置き＝取りこぼし防止。
     cloud のフラグを付け忘れると同じ発話を毎回再判定してしまうので、読めた分は必ず付ける）。
   - 新しい domain を書いた回だけ `--allow-new-domain` を付ける。
   - 検証エラー（exit 2）なら rows を直して再実行する（何も書き込まれていない）。
   - 0 件の回も `[]` で実行してよい（自動クローズ等の整備が走る）。
4. **接続サービスも同様に**: `watari connector list` の各サービスについて——
   組み込みは `watari connector read <name> --json`（`--since` 省略で続きから）で読み、
   同じ基準で判定して ingest に `--advance-ext <name>=<そのサービスで処理した最新 ts>` を付ける。
   read が失敗（非ゼロ終了）したサービスのフラグは付けない。カスタム宣言のものは、その
   `read` 指示に従って自分のツールで読む。scope が cloud のサービスは
   「**接続したパソコンが読み取り担当**」——このパソコンに接続情報があるものだけを読む。
5. **検査（機械）**: `watari audit`。「直したほうがよい点」が出たらその場で直してから終える
   （まとめの食い違いは `watari regen` で直る）。
